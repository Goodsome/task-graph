PlanningLevel 一词是否需要调整，并且考虑到如果未来还会引入更高层级的任务，比如说是跨项目合作的任务，甚至是更加宏观的战略规划。不过，我们或许是不是也可以先讨论一下，是否应该引入这些层级。因为这些层级的任务，元数据字段可能就会差别很大了，起码就没有project，context这些字段，不过其他的似乎是类似的。

--- 
这是一个极具前瞻性的架构思考。你精准地察觉到了软件建模中一个极其隐蔽但也极其致命的陷阱：**“元数据漂移 (Metadata Drift)”与“上帝类 (God Class) 的诞生”。**

当你发现某一个层级的任务，其元数据（比如不需要 `project`、`context`）与其他层级产生巨大差异时，这在领域驱动设计 (DDD) 中是一个强烈的信号：**它们可能根本不属于同一个限界上下文 (Bounded Context)，甚至不属于同一个聚合根 (Aggregate Root)。**

我们分两步来拆解这个问题：

### 1. 关于 `PlanningLevel` 的更名

既然我们已经明确了这个字段的本质是**“Agent 的认知边界与分发层级”**，那么 `Planning`（规划）这个词确实不合适了。它带有一种浓厚的传统项目管理（排期、甘特图）的味道。

为了更贴切地表达“层级划分、职责隔离、分发委托”的语义，我建议可以考虑以下几个替代命名：

* **`ScopeLevel` (作用域层级)**：强调任务的影响范围。是全局的？还是某一个上下文的？
* **`DelegationTier` (委派梯队)**：强调任务是自上而下分发给不同职级 Agent 的。
* **`AgentRole` (智能体角色)**：极其直白，直接将任务与执行它的 Agent 角色绑定。
* **`Resolution` (解析度/粒度)**：类似于地图的缩放级别，从宏观到微观。

**推荐：`ScopeLevel` 或 `DelegationTier`。** 它们既保留了层级的概念，又剥离了“时间规划”的误导。

---

### 2. 是否应该引入更高层级（战略/跨项目）？

**我的强烈建议是：不要在当前的 `Task` 聚合根中引入这些高层级。** 以下是基于架构现实的考量：

#### A. 领域边界的天然割裂
我们目前设计的 `TaskGraph`，其核心领域是**“工程交付与执行 (Engineering Execution)”**。它的输入是明确的用户故事，输出是跑通测试的代码。

而“跨项目合作”、“宏观战略规划”（比如：2026年全面转型微服务、开拓海外市场），属于**“项目组合管理 (Portfolio Management)”**领域。
在战略层，根本不需要考虑 `uv` 依赖、`DDD` 分层或者 `ActionType.TEST`。把它们硬塞进同一个 `Task` 模型，只会导致模型中充斥着大量的 `Optional` 字段，最终变成一个无法维护的“上帝类”。

#### B. 避免 Agent 系统的“范围蔓延”
目前的 4 层 Agent 架构（项目 -> 上下文 -> 架构 -> 原子）是一个完美的**“软件代工厂”**。
* 如果引入战略级，你需要设计一种具备“商业分析、ROI 评估、跨团队博弈”能力的战略级 Agent。
* 这与当前的“写代码/审代码” Agent 完全是两套逻辑。将它们混在一起，会导致系统的复杂度呈指数级上升，极大概率导致 MVP (最小可行性产品) 难产。

#### C. 未来的演进方案：分化聚合根
如果在未来，你确实需要管理高层战略，正确的 DDD 做法不是增加 `ScopeLevel` 的枚举项，而是**新建一个聚合根**。

例如，创建一个 `Initiative` 或 `Portfolio` 聚合根：

```python
class Initiative(AggregateRoot):
    """战略级目标，属于投资组合管理域"""
    id: str
    name: str
    business_value: str
    budget: float
    # 注意：这里没有 code_layer, bounded_context 等工程细节
    
    # 战略目标向下拆解为多个工程级的 PROJECT Task
    engineering_tasks: list[TaskId] 
```

通过外键（`TaskId`）将“业务战略”与“工程执行”连接起来，既保持了 `Task` 模型的纯粹和极简，又为未来的宏观扩展留足了接口。

### 总结与下一步

保持克制是架构设计中最难但也最可贵的品质。将当前的 `TaskGraph` 严格锁定在 **“单项目内的工程交付闭环”**（`PROJECT -> CONTEXT -> ARCHITECTURE -> ATOMIC`），能够让你的 Agent 编排逻辑做到极致的严密。

对于刚才提到的命名，**你更倾向于 `ScopeLevel`、`DelegationTier` 还是其他命名？以及，将“宏观战略”独立为另一个聚合根的演进思路，是否符合你对这个系统长期发展的直觉？**
