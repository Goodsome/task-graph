# Planning 领域业务叙事 (Domain Narrative)

## 1. 领域愿景 (Context Vision)

`Planning` 上下文是系统的“大脑”，其愿景是**通过结构化的 DAG (有向无环图) 模型，为 AI Agent 提供具备深度上下文和优先级感知的行动蓝图**。

与传统的线性任务列表不同，`Planning` 强调任务之间的**因果依赖**和**价值产出**。它通过四级严格的职能边界定义，实现了从战略设计到代码落地的端到端闭环，并确保研发流程在复杂的依赖网路中始终沿着最优路径（Highest ROI）前进。

## 2. 核心业务流程 (Core Workflows)

### A. 职能层级定义 (Scope Levels)
系统通过四级任务定义明确了研发的不同阶段与职责：
1.  **Project 级 (战略层)**：维护整个项目的战略设计。负责划分核心域、支撑域、定义北极星目标及限界上下文映射图（Context Map）。
2.  **Context 级 (战术层)**：维护特定限界上下文内的战术设计。负责编写领域叙事、统一语言、聚合根定义及上下文内的技术实现蓝图。
3.  **Architecture 级 (架构层)**：负责特定上下文内各个架构层（Domain, Application, Interfaces, Infrastructure）的详细技术设计与原子任务派发。
4.  **Atomic 级 (执行层)**：负责单一职责的代码落地，是最小的可执行单元。

### B. 递归拆解与递归验收流 (Recursive Decomposition & Review)
所有需求从 `Project` 层级出发，遵循“设计 -> 验收 -> 拆解 -> 执行”的递归模式：
1.  **设计先行**：每一层级的负责人（Agent）接收任务后，首先完成该层级的设计产出（如战略文档或架构图）。
2.  **上层验收**：任务完成后由上层级负责人（Agent）根据**验收标准 (Acceptance Criteria)** 进行 Review。验收标准以 BDD 格式（Given/When/Then）随任务创建时一同录入，作为评判任务完成质量的结构化依据，并为后续自动化测试生成提供元数据。
3.  **激活拆解**：验收通过后，若判断需要进一步下钻，系统会再次激活该层级的负责人，将其状态转为 `DECOMPOSING`，并创建下一层级的子任务。
4.  **向上递归**：父任务的最终完成（`DONE`）取决于其所有子任务的完成状态。只有当所有原子任务完成并通过验收，才会向上递归触发架构层、战术层直至战略层的任务闭环。

### C. 基于 ROI 的执行优先级决策 (ROI-Based Prioritization)
在面临多个已解锁（`READY`）的任务时，系统通过 `Value / Effort` 模型辅助决策：
*   **Value (价值)**：反映任务对项目的战略意义或紧急程度。
*   **Effort (成本)**：反映任务的预估执行难度（斐波那契数）。
*   **业务决策**：Agent 调用 `suggest_next_action` 工具，系统动态计算并返回当前价值密度最高的行动路径，确保资源永远投入在收益最大的任务上。

## 3. 典型用户故事 (User Stories)

*   **作为战略 Agent**，我根据原始 Issue 开启了一个 `Project` 级的战略设计任务，在完成后提交给人类或高级 Agent 审核，并在审核通过后开始将其拆解为多个 `Context` 级的战术任务。
*   **作为战术 Agent**，我接收到 `Context` 任务后，专注于该领域内的业务叙事与通用语言定义，并在我的设计产出被父级任务验收后，进一步拆解为 Domain 层或 Application 层的 `Architecture` 任务。
*   **作为开发 Agent**，我执行具体的 `Atomic` 任务（如编写一个 Pydantic 模型），并在我提交产出后，系统自动触发父级架构任务的进度更新与后续验收。
*   **作为规划 Agent**，我在创建任务时为其编写结构化的验收标准（BDD 格式），明确该任务的 `Given / When / Then` 完成条件，以便后续由 Agent 或 CI 工具自动将其转化为对应类型的测试用例（单元、集成或端到端）。
